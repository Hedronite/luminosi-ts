# The LuminosiTS stack

How the languages and tools in LuminosiTS relate: which ones the browser understands, which ones compile into those, and which ones never ship at all. The [manifesto](README.md) says what LuminosiTS is; this file says what it is made of.

---

## 1. What the browser understands

A browser natively runs four kinds of thing. Everything else in this repo exists to produce them.

| Native | Role | LuminosiTS uses it for |
|---|---|---|
| **HTML** | Structure and semantics | Catalog pages, Astro sites, accessible controls around every 3D view |
| **CSS** | Presentation and layout | All styling, generated by Tailwind or written by hand |
| **JavaScript** | Logic and interactivity | Everything TypeScript compiles to |
| **GPU APIs** (WebGL 2, WebGPU) with their shader languages (GLSL, WGSL) | Drawing 3D | Three.js renders through these; shaders run on the GPU |

Assets ship as files the browser or GPU decodes directly: SVG for icons and glTF binary (`.glb`, meshopt-compressed) for models. The build has no texture, font, image or Blender pipeline yet.

---

## 2. What compiles into them

| Tool | Kind | Written as | Ships as |
|---|---|---|---|
| **TypeScript** | Language (typed JavaScript) | `.ts` | JavaScript; types are erased |
| **TSX** | TypeScript with JSX markup | `.tsx` | JavaScript (React calls) |
| **React** | UI library | TSX components | JavaScript in the app bundle |
| **Three.js** | 3D library | TypeScript calls | JavaScript that drives WebGL or WebGPU |
| **React Three Fiber** (R3F) | React renderer for Three.js | TSX scene components | JavaScript, same as React |
| **TSL** | Three.js shading language, written in TypeScript | `.ts` node graphs | GLSL or WGSL, generated at runtime for the active GPU backend |
| **Tailwind CSS** | CSS framework | Utility classes in markup, tokens in `@theme` | Only the CSS rules actually used |
| **Astro** | Web framework | `.astro` components | HTML and CSS; JavaScript only for islands |
| **Zod** | Runtime validation | Schemas in TypeScript | JavaScript that checks data at the boundary |

### An Astro component, layer by layer

```astro
---
// TypeScript (frontmatter): runs at build time, never in the browser.
interface Props {
  title: string;
  isFeatured?: boolean;
}
const { title, isFeatured = false } = Astro.props;
---

<!-- HTML for structure, Tailwind classes for style. -->
<!-- Class names are complete strings, so Tailwind can see them. -->
<article class={isFeatured ? "rounded-lg border border-blue-600 bg-blue-50 p-6" : "rounded-lg border border-gray-200 p-6"}>
  <h2 class="text-xl font-bold tracking-tight">{title}</h2>
  <p class="mt-2 text-gray-700">Rendered by Astro into plain HTML.</p>
</article>

<!-- Plain CSS, scoped to this component automatically. -->
<style>
  article { transition: transform 0.2s ease-in-out; }
  article:hover { transform: translateY(-2px); }
  @media (prefers-reduced-motion: reduce) {
    article { transition: none; }
  }
</style>
```

Each class string is written out in full. Tailwind finds classes by scanning source text, so a name built at runtime, such as `` `bg-${color}-600` ``, is never generated and is missing in production.

### A 3D island on an Astro page

WebGL cannot render on the server, so a React Three Fiber scene is a client-only island. A static fallback (here an SVG wireframe drawn at build time) is what loads first, and it stays if JavaScript never runs.

```astro
---
import { platonic } from "@hedronite/lts-primitives";
import Wireframe from "../components/Wireframe.astro";
import Layout from "../layouts/Layout.astro";
// The site's own island: a React component (apps/site/src/components/Showcase.tsx)
// that draws library solids with @hedronite/lts-adapters.
import Showcase from "../components/Showcase";
---

<Layout title="Showcase">
  <h1 class="text-3xl font-semibold">Showcase</h1>
  <Showcase client:only="react">
    <div slot="fallback"><Wireframe shape={platonic("icosahedron")} size={120} /></div>
  </Showcase>
</Layout>
```

## 3. Build pipelines

```
  SOURCE                         TOOL                              OUTPUT
  ─────────────────────────────  ────────────────────────────────  ─────────────────────────────
  packages/*/src/*.ts            tsc                               dist/*.js + *.d.ts (ESM)
  apps/catalog/src/*.tsx         Vite + @vitejs/plugin-react       hashed JS bundle
  *.astro                        astro build                       static HTML (+ island JS)
  Tailwind classes, @theme       @tailwindcss/vite                 one minimal CSS file
  TSL node graphs                Three.js, at runtime              GLSL (WebGL) or WGSL (WebGPU)
  assets/src/models/*.json       glTF Transform + meshopt          tools/assets/dist/models/*.glb
  assets/src/icons/*.svg         SVGO, then codegen                icon modules (.ts, ./react)
```

- **Libraries are not bundled.** Packages ship ESM and type declarations; the app that uses them does the bundling, so it can tree-shake down to the pieces it imports.
- **Apps bundle with Vite.** Three.js and R3F load through a dynamic `import()`, so the first paint does not wait for them.
- **Sites build with Astro.** Pages are static HTML unless a component opts into an island.
- **Assets are build outputs.** Optimized `.glb` files are regenerated from their scene descriptions in `assets/src/models`, never edited by hand.

### The WebGPU lane

The default `bun run e2e` and CI draw with software WebGL (SwiftShader), so they run on any machine and never reach WebGPU: three's WebGPU renderer finds no adapter there and falls back to WebGL 2. The WebGPU lane runs the same stages on the real thing.

```bash
bun run e2e:webgpu
```

- **Where.** On a machine with a GPU: Apple silicon through Metal is what it was written on. A machine without one fails the first check, with the reason (`navigator.gpu is missing`, `requestAdapter() returned null` or `a software adapter (…)`), instead of passing on a fallback.
- **What it does.** Builds the catalog, serves it on `localhost` (a secure context, which `navigator.gpu` needs) and runs one Playwright project, `webgpu`, in Chromium started with `--enable-unsafe-webgpu --use-angle=metal`. On the shader viewport, the Effects stage and the playground it asserts `data-backend="webgpu"`, a drawn frame (`data-frames` above zero, and growing on the two stages that animate) and a canvas that holds a picture. Every 3D canvas writes `data-backend` (`webgpu` or `webgl`) beside `data-frames`, so a test can tell which renderer drew it.
- **Another origin.** Set `E2E_CATALOG_URL` to a catalog served over HTTPS and it runs against that instead of starting a server.
- **Posters.** `bun run stills posters` makes the frames and then turns each into a WebP at twice the gallery tile (112 by 112), with `assets/posters/manifest.json`: for each asset its path, size and an input hash of the asset id, its default parameters, the neutral look, the poster size and `RIG_VERSION`. The posters are made by this script and committed, never edited by hand; `bun run validate` fails a 3D asset with no poster, a poster over its byte line in `assets/budgets.json`, one of the wrong size, one whose hash no longer matches (the asset's defaults, the look or the rig moved on), or one left for an asset that is gone. The gallery shows them from `/posters/<id>.webp` (the catalog's build copies the folder), lazily, at the tile's size with the asset's name as alt text, and draws the stand-in shape only when a file does not load.
- **Why it is not in CI.** Hosted runners have no GPU. Their only WebGPU adapter is a software one (SwiftShader), which the lane refuses, which would prove nothing about the GPU path and cost minutes on every pull request. The `webgpu` project exists only when `LTS_WEBGPU_LANE=1` (the script sets it), so `playwright test` and the CI workflow never see it. Nothing schedules it either: run it by hand before a change to the renderer, the shaders or the screen effects merges.

### Still frames

The still-frame rig draws one 3D asset the same way every time, so a picture of it can be compared, committed and trusted. The posters and the golden images are made from it.

```bash
bun run stills                                      # builds the catalog, writes one PNG per 3D asset to test-results/stills
STILLS_OUT=/some/dir bun run stills                 # the same, into a directory of your choosing
bun run --filter tool-stills compare <dir> <dir>    # two runs, asset by asset: identical, or by how much not
bun run stills posters                              # the same, then the gallery posters: assets/posters/<id>.webp and manifest.json
```

- **What a frame is.** `still.html?still=<asset id>` is a page of its own (source: `apps/catalog/src/Still.tsx`) that the catalog's build makes with a second Vite run (`apps/catalog/vite.still.config.ts`) into the same `dist`. Nothing of it is in the chunks the catalog's visitors load or in any bundle `assets/budgets.json` counts: an entry added to the catalog's own build shares modules with the 3D views, the bundler then moves them into shared chunks, and the budgeted bundles change for a page nobody visits (it did, by 800 bytes). It draws the asset on a fixed 512 by 512 stage at device pixel ratio 1, from a fixed camera per kind (the one its detail view starts from), lit as that view lights it, in the neutral look, with the asset's default parameters. Frames are stepped by hand: 60 frames of 1/30 s, so the stage clock stands at 2.00 s and no wall-clock time reaches the picture (a surface shader reads its time from a clock the rig writes, not from three's). The lens screen effect has its pointer held at the middle of the stage. Generators that take a seed get theirs from the asset's parameters; `Math.random` is lent a seeded sequence besides. The stage says `data-still="ready"` (with `data-frames="60"` and `data-time="2.00"`) only after the asset has loaded and the last frame is drawn, and `data-still="error"` with the reason when it cannot be. `data-rig` carries the rig's version, which a poster's input hash will include: bump `RIG_VERSION` in `Still.tsx` when the rig's picture changes for a reason other than an asset.
- **Which assets.** Every asset in the registry but the icons: the list comes from `loadRegistry()` when the capture starts, so a new asset is captured with no edit anywhere. A kind with no camera in `Still.tsx` fails its test instead of being skipped.
- **Where.** On a machine with a GPU, as the WebGPU lane is: Apple silicon through Metal, Chromium started with `--enable-unsafe-webgpu --use-angle=metal`, one worker. The `stills` Playwright project (testDir `tools/stills/src`) exists only when `LTS_STILLS=1`, and then it is the only project. Each asset is a test that waits for `data-still="ready"`, screenshots the stage element and writes `<id>.png`; it fails on any console error or a picture that is not 512 by 512.
- **Determinism.** Two runs on the same tree on the same machine give byte-identical PNGs (`compare` exits 1 and prints, for each picture that differs, the pixels changed and the largest and mean channel step, so a noise ceiling can be ruled from numbers). A different machine, GPU or browser build can differ: regenerate goldens and posters where they are checked.
- **Why it is not in CI.** Hosted runners have no GPU, and a software adapter draws a different picture from Metal's. The default `bun run e2e` and the CI workflow never see the project.

### Golden images

Every 3D asset has a golden image, a lossless PNG the still-frame rig drew for it (`e2e/golden/<id>.png`, 512 by 512). A check draws each asset again and compares the frame with its golden, so a change that alters how an asset looks fails a test instead of passing unseen. Two checks, one spec (`e2e/golden.spec.ts`):

```bash
bun run e2e:golden          # strict: the real GPU, on the machine the goldens were made on; never in CI
bun run e2e:golden:loose    # loose: software WebGL, what CI runs in its `golden` job
bun run goldens             # regenerate every golden, by the rig (bun run stills into e2e/golden)
```

- **Strict.** The `golden` project (`LTS_GOLDEN=1`, Metal, one worker, like the rig) fails an asset when any pixel differs from its golden at all. That is the noise: the rig's frames are byte-identical from run to run (STACK.md, "Still frames"), and the 74 goldens are byte-identical across two regenerations. A different machine, GPU or browser build may differ, and then the goldens are regenerated there.
- **Loose.** CI has no GPU, and software WebGL draws a slightly different picture (a different renderer, a different anti-aliasing), so the `golden-loose` project (`LTS_GOLDEN_LOOSE=1`, SwiftShader) compares coarsely, in 16 by 16 blocks of 32 pixels, on three numbers (`e2e/golden/metrics.ts`): the mean over the blocks of the difference in mean colour (`tone`), the largest such difference in any one block (`local`), and the mean difference in subject coverage, the share of a block that is not the stage's background (`coverage`). A frame fails above any bar.
- **The bars, and their margin.** The bars came from the machine the goldens were made on, for all 74 assets (SwiftShader frame against GPU golden): the largest distances were tone 0.183 (dress-watch), local 2.567 (dress-watch) and coverage 0.0033 (soap-film). The bars are tone 0.28, local 3.9 and coverage 0.005, about 1.5 times those. CI's Linux runner agreed for 72 assets (largest tone 0.191, local 2.601, coverage 0.0033) and put two screen effects further from their goldens, ascii (tone 0.439, coverage 0.0205) and crystallize (tone 0.263, coverage 0.0055), so those two have bars of their own in `metrics.ts`: ascii tone 0.55, coverage 0.026; crystallize tone 0.4, coverage 0.0083. The rule for every asset is a margin of 1.2 on both sides (`MARGIN`): a clean frame measures at most its bar over 1.2, and each plant at least 1.2 times its bar. The spec enforces it in the loose project, so a bar or a rendering that erodes it fails CI. CI prints every asset's distances in its log (the `golden` job). Over four CI runs the distances did not differ at all (the largest spread, over every asset, frame and metric, was 0), so the margins below are exact for a runner of that kind. The bars of ascii and crystallize are set for that runner, so the loose project on a Mac with a GPU (where the software frame is much nearer the golden: ascii tone 0.023) still passes every clean frame but fails ascii's missing-part and moved-camera plants on the margin: the loose check is CI's, and its margins are read from the CI log.
- **Plants.** For every asset, in both modes, the spec also draws four plants on the page the rig drew and requires the check to fail each: a blank canvas (the canvas hidden), a recoloured subject (a CSS colour filter over it), a missing part (a 160 pixel block of the middle painted over with the background) and a moved camera (the picture shifted 16 by 10 pixels and enlarged 4%). Strictly, the weakest plant still changed 3259 pixels (missing part, dissolve). Loosely, on CI's distances, the weakest plant of each kind reached this many times its bar: blank canvas 5.2, recoloured subject 3.7, missing part 1.35 and moved camera 1.24, all of them on ascii (every other asset: 11.4, 6.8, 1.41 and 4.1 or more; the weak ones are surfaces close to the background colour, which hide little). The weakest clean frame, ascii, sits at 0.80 of its bar, a margin of 1.25.
- **Updating a golden.** Never by hand: change the asset, run `bun run goldens` on the GPU machine, and list the changed ids in the PR (`git status e2e/golden`). A golden with no asset in the registry fails a test, and an asset with no golden fails its own.
- **Size.** The goldens take 4,492,739 bytes together (the largest, crt, 527,328); `assets/budgets.json` budgets both under `goldens`, and `bun run validate` checks them.
- **Why the strict check is not in CI.** A runner has no GPU, and a software frame is not the GPU's: it would fail every asset, or its bar would pass a regression. The strict project exists only when `LTS_GOLDEN=1`; the default run, the container run and the CI job that runs the loose project (`LTS_GOLDEN_LOOSE=1`) never see it.

### Scene document

A composition is one JSON document, `lts-scene` version 1, in `@hedronite/lts-scene` (`packages/scene`). The root and `./emit` are pure data: zod and `@hedronite/lts-core` only, no three.js, no `three/webgpu`, no React, so a document can be read, checked, migrated and written anywhere, a CLI or a server included. What builds it into pixels (`./three`) and what writes it as code (`./emit`'s TSX and vanilla) are the next two entries, and the round trip below holds the two pictures equal.

```jsonc
{
  "format": "lts-scene", "version": 1,
  "look": "neutral",                      // a look id, or { base, accent, metal, glass, emissive } as #rrggbb
  "seed": 0,                              // reserved: nothing reads it yet
  "nodes": [{
    "id": "node-1", "parent": null,       // a node id, or null; no cycles
    "position": [0, 0, -0.85], "rotation": [0, 0, 0], "scale": [0.5, 0.5, 0.5],
    "asset": { "kind": "primitive", "id": "platonic-cube" },
    "surface": { "material": "metal" }    // or { "shader": "toon", "params": { "bands": 4 } }
  }],
  "lights": { "rig": "studio", "intensity": 1 },
  "environment": { "kind": "studio" },
  "camera": { "position": [0, 2.2, 5.5], "target": [0, 0, 0], "fov": 40 },
  "effects": [{ "id": "dither", "params": { "cell": 4 } }],   // kept in document order, each once; the effect library sets the order they run in
  "ink": "look"                                               // look | accent | emissive | glass
}
```

- **Nodes.** An `asset` is `{ kind, id, params? }`, and its `kind` is one of three. A `primitive` has a `surface`, a material or a surface shader, each with its own `params`. A `framed` solid, the adapters' `FramedSolid`, has a primitive's id, a required `edges: { material }` and a `surface` that is the faces; `edges` belongs to `framed` and to nothing else. An `object` is a library object, the registry's own `framed-solid` among them, and takes its look from `params` (`{ "material": "glass" }`), not from a `surface`; `checkRefs` rejects a surface on an object. `rotation` is Euler angles in radians, x, y, z. A child's transform is relative to its parent's.
- **The root API** (`@hedronite/lts-scene`). `parseScene(json)` reads a value or JSON text of the current version and returns `{ ok: true, scene }` or `{ ok: false, issues }`, each issue a `path`, a short named `code` (`missing-field`, `wrong-type`, `wrong-value`, `out-of-range`, `bad-format`, `unknown-key`, `no-match`, `wrong-format`, `unsupported-version`, `invalid-json`) and a sentence; it never throws on user input, and `migrate` names its issues the same way, version 0's included. `migrate(json)` does the same for any version. `checkRefs(scene, resolve)` takes the lookup from the caller (`resolve(kind, id)` returns something with the asset's parameter schema, or nothing), so the root never imports a registry's builders, and returns the issues the document's shape cannot show: `unknown-primitive`, `-object`, `-material`, `-shader`, `-effect` and `-look` for an id that is not there, `unknown-param` for a parameter the asset's schema does not have, `invalid-param` for a value outside it, `surface-on-object` for a surface on an object node, `duplicate-effect` for an effect twice in the stack, `duplicate-id`, `missing-parent` and `cycle`. `ringLayout(count)` is the ring the playground has always put its placements on.
- **Migration.** `migrate` runs a table of steps, one per old version, each reading its own version's shape and writing the next's. Version 0 is the playground's `toJson` output from before the format existed: it declares no format or version, has no ids, positions, camera, look or seed, and lists its effects as bare ids. It becomes `node-1`, `node-2` and so on at the `ringLayout` positions, scaled 0.5 (0.6 for an object) as the playground drew them, each turned by the playground's view tilt `[0.3, 0.5, 0]` so a migrated scene draws as it was seen, in the default look and the playground's camera. Every version has a fixture in `packages/scene/fixtures` (`v0.json`, `v1.json`), and a test fails for a version without one. A new version adds one step, one fixture and nothing else.
- **Canonical text.** `toCanonicalJson` (`@hedronite/lts-scene/emit`) writes a document with two-space indent and one list of key names that fixes the order everywhere (`format`, `version`, `look`, `seed`, `nodes`, `lights`, `environment`, `camera`, `effects`, `ink`, then `kind`, `id`, `parent`, `position`, `rotation`, `scale`, `asset`, `surface`, `edges`, `material`, `shader`, `params`, `rig`, `intensity`, `target`, `fov`, and the palette's five), a key not on the list (most parameter names) alphabetically after those, so a parameter named `id` or `material` is written at its place on the list and not alphabetically, numbers in their shortest round-trip form (negative zero as `-0`), a list of numbers on one line, and a final newline. Equal documents give equal text, and the text reads back as the same document. The fixtures are in that form, and a test holds them to it.
- **Editing.** `addNode`, `removeNode`, `setTransform`, `setSurface`, `setEffects`, `setInk`, `setLights` and `setLook` (`packages/scene/src/edit.ts`, from the root) take a document and return a new one; the input is never written to, and nothing in the output is shared with it that a later edit could change. Each returns what `parseScene` returns: `{ ok: true, scene }`, or `{ ok: false, issues }` for an edit that would leave a document that does not read, so a field a person types into can hand its value straight to an edit, and none of them throws. An `ok` document has been through `parseScene` and holds none of the structural problems `checkRefs` finds without a registry (`duplicate-id`, `missing-parent`, `cycle`, `duplicate-effect`, `surface-on-object`), and `checkRefs` with the caller's lookup finds nothing more as long as the ids and parameters the edit brought are the registry's. The edits name one code of their own, `unknown-node`, for a node id the document does not have. `addNode` appends a whole node (its id new, its parent a node already there); `removeNode` takes the node and every node that stands in it, however deep, so no node is left with a parent that is gone; `setTransform` replaces the position, rotation or scale it is given and keeps the rest; `setSurface` with `undefined` takes a surface away, and on an object is `surface-on-object`; `setEffects` takes the whole stack in its order; `setLights` takes the fields of the rig it is given. Nothing re-rings a scene: an added node is at the position it was given.
- **History.** `createHistory`, `push`, `undo`, `redo`, `canUndo`, `canRedo` and `endGesture` (`history.ts`) keep what can be undone as `{ past, present, future, gesture }`: documents and one string, so the whole history survives `JSON.stringify` and `JSON.parse` and can hold no built object (`-0` is written `0` by `JSON.stringify`; `toCanonicalJson` keeps it). A history holds at most `HISTORY_CAP` (100) steps back, and the 101st change drops the oldest. A `push` with a key that is the key of the push just before it, with no undo, redo or `endGesture` between, folds into that step: one node's one field during one drag is one step, and the caller ends a gesture (or gives the next one another key) when it is over. A push with no key is always a step, even of a document equal to the present one, so a caller that does not want a step for a change that changed nothing compares first. `push` forgets what was undone; `undo` and `redo` with nothing to step to return the history they were given.
- **Links.** `encodeScene(scene)` and `decodeScene(text)` (`share.ts`, from the root) write a document as text that fits in an address and read it back. The text is `s1.` (the link format's version) and then the base64url, without padding, of the document's canonical JSON deflated (raw deflate, no header). Deflate is the platform's own, `CompressionStream` and `DecompressionStream` (every browser and Node have them), so the root takes no library for it and for the same reason both functions are asynchronous. `decodeScene` inflates, runs `migrate` (so a link made from a version 0 document opens as a version 1 one) and returns what `parseScene` returns; it never throws, whatever it is given, and leaves the space around a pasted link off. A link is at most 16 KiB (`SHARE_LIMITS.link`, 16,384 characters, prefix included) and its document at most 256 KiB inflated (`SHARE_LIMITS.document`, 262,144 bytes); inflation stops at the limit, so a small link that holds a huge text costs no more than the limit to refuse (eight million zero bytes deflate to about 8 KB, a link of 10 KB, and are refused after 256 KiB). A link that is not good is one named issue, at the root of the document: `link-too-long` (read by length, not at all), `not-a-link` (it does not start with `s1.`, so a later format version is this too), `bad-encoding` (not base64url), `bad-compression` (not deflate data), `document-too-large`, and then `invalid-json` and the rest of `migrate`'s codes for a document that inflates and does not read. `encodeScene` does not refuse a document whose link is over the limit; a caller that shows a link compares its length with `SHARE_LIMITS.link`, because `decodeScene` will refuse it.
- **Boundaries.** Two rules in `.dependency-cruiser.cjs` and a test (`boundary.test.ts`) hold the line. The root and `./emit` may import zod and core and nothing else; `src/three.ts` may import core, the registry, tokens and the `./three` entries of materials, primitives, objects, shaders, postfx and scenes, and never adapters or React. The editing, history and link modules are in the root and so under it (the codec uses the platform's stream globals, which are no import). The test walks what the two entry files reach and fails on any other package, and a planted import of three, `three/webgpu`, React or adapters shows it does. Nothing in the catalog's gallery imports the package.
- **The fixtures for the round trip.** `primitives-in-materials`, `framed-solid-shader`, `object-effects-ink` and `transform-hierarchy` are the documents the still-frame proof draws, built from the document and from the code emitted for it; the last has a parent with a turn and a non-uniform scale, a child turned inside it, and a parent listed after its child, so a wrong rotation order or a wrong parent-relative transform changes the picture. A node id is any run of letters, digits, underscores and dashes that does not start with a dash (`constructor` and `__proto__` are ids like the rest), so nothing that reads a document may use an id as an object key or an identifier.

### The scene round trip

A scene document is drawn twice, and the two pictures are held equal. `still.html?scene=<fixture>&via=doc` draws a fixture of `packages/scene/fixtures` through `createScene` (`@hedronite/lts-scene/three`); `via=code` draws the vanilla module `toVanilla` emitted for it (`e2e/scenes/generated/<fixture>.ts`, made by script and committed). The page is the still-frame rig's scene mode (`apps/catalog/src/sceneStill.ts`): the same fixed square stage, device pixel ratio 1 set before either build (the screen effects read it when they are built), one paused clock at time zero that is never written, one reduced-motion setting, a seeded `Math.random`, and 60 frames stepped by hand. The fixtures are `primitives-in-materials`, `framed-solid-shader`, `object-effects-ink` and `transform-hierarchy`; their goldens are `e2e/scenes/<fixture>.png`, made from the doc frame.

```bash
bun run scenes:generate   # build, then write the emitted modules from the fixtures (the emitter is read from dist, so these three build first)
bun run scenes:check      # build, then fail when a committed module is not what the emitter writes now
bun run scenes            # generate (building first), then write the scene goldens (the GPU machine; list the fixtures in the PR)
bun run e2e:scenes        # strict, below: the real GPU, never in CI
bun run e2e:scenes:loose  # loose, below: software WebGL, what CI runs in its golden job
```

- **Strict** (`scenes` project, Metal, one worker): for each fixture the doc frame, the code frame and the golden are the same picture, to the pixel. Three plants are made in the document, so in the code emitted for it (`bun run scenes:plants` writes them into `e2e/scenes/plants/`, never committed): a node moved, an effect dropped, a parameter changed (the first effect's parameter, else a surface's, else an asset's). Each must change the code frame, and the spec fails if one does not apply where it should. Where a fixture has no effects or parameters the plant is not made; every fixture has a node to move.
- **Memory.** After the scene is freed, and after five more builds and frees, `renderer.info.memory` holds what a renderer that drew only an empty scene holds, counts only (the sizes in bytes beside them move with the environment bake), plus the leftovers of that fixture: the environment bake's one texture always, and one more only where the fixture has transmissive glass (`e2e/scenes/memory.ts` reads it from the document's materials: `primitives-in-materials` and `transform-hierarchy` keep two, the other two keep one). The five readings are asserted identical first, so a resource leaked on every cycle fails that on its own; then each reading, the first free's included, is held to the bound. Raw zero is not reachable. Without the fix that frees the screen effects' scene pass, a build and free with effects leaves a render target and two textures every cycle, and this check fails on `renderTargets`.
- **Stale and hand-edited modules.** `e2e/scenes/stale.spec.ts` is in the default run and in CI: each committed module must be exactly what the emitter writes for its fixture, no module may be left without one, and each plant must change the emitted text. A module edited by hand, or left behind by a change to a fixture or the emitter, fails it; `bun run scenes:generate` writes them again. The catalog build lists the fixtures, the generated modules and the planted modules as inputs (`turbo.json`), because they sit outside its package and a cached build would replay stale ones.
- **Loose** (`scenes-loose` project, SwiftShader, what CI runs after the loose golden check): the doc frame against the golden with the golden check's three numbers and its four plants (a blank canvas, a recoloured subject, a missing part, a moved camera), and the margin of 1.2 on both sides: a clean frame at most its bar over 1.2, each plant at least 1.2 times its bar. The bars are the golden check's (`e2e/golden/metrics.ts`); they are CI's, so they are read from the distances the job prints, never from a Mac run, which draws nearer the golden. Three CI runs of the same build printed the same distances for every fixture, frame and metric (a spread of 0). Three fixtures sit under the common bars (largest clean tone 0.0805, local 1.04, coverage 0.00047); `primitives-in-materials`, the one with glass, measures 4.95 in `local` against the common 3.9, so it has a `local` bar of 7.5 of its own in `metrics.ts` (a clean frame at 1.52 times under it, its weakest plant 5.1 times over it, on tone). The weakest plants of each kind, as times the bar: blank canvas 9.3 and recoloured subject 3.2 (both `object-effects-ink`, whose subject is small), missing part 9.3 (`object-effects-ink`) and moved camera 7.7 (`object-effects-ink`); every other fixture is further over. Every fixture is at least 1.2 on both sides.
- **Size.** The four scene goldens take 123,194 bytes (the largest, `framed-solid-shader`, 80,916). `measureGoldens` adds `e2e/scenes` to `e2e/golden` for the one `goldens` line of `assets/budgets.json`: 4,615,933 of 4,700,000 bytes, the largest 527,328 of 560,000.

## 6. Choosing between them

- **The platform first.** If HTML or CSS can do it (a dialog, a popover, a container query, a transition), don't add JavaScript for it.
- **Astro for pages people read**, such as sites, docs and showcases. **Vite + React for apps people use**, such as the catalog (with its playground).
- **Three.js directly in packages; R3F only at the edges.** The library stays usable without React.
- **TSL for new shaders.** One source runs on both WebGL and WebGPU. Write raw GLSL only for WebGL-only effects or ports.
- **Tailwind tokens, not raw values.** Colors and spacing come from `@theme`, so a preset can swap the look without touching components.
- **Validate at the boundary.** Anything from outside (manifests, fetched JSON, environment) passes through a Zod schema before the rest of the code trusts it.
